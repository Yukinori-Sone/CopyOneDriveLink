# 多重起動防止(Mutex)の不具合調査記録

`OneDriveTrayApp.ps1`に多重起動防止を実装した際、「常に多重起動と誤判定され、
1つ目の起動でもタスクトレイアイコンが一度も表示されない」という不具合が
発生した際の調査記録。

## 症状

- タスクトレイアイコンが常に表示されない。
- どんなタイミングで起動しても、必ず「OneDrive共有リンクコピーは既に
  タスクトレイで起動中です」という警告ダイアログが出る（本当に1つ目の
  起動であっても）。
- `tasklist`で確認しても該当プロセスが既に終了しており、多重起動している
  形跡が無い。
- `.NET`例外としてもクラッシュとしても記録が残らない
  （`try/catch`にも掛からず、Windowsのイベントログにも記録が無い）。

## 誤った仮説（調査の過程で検討し、否定したもの）

1. **`.ico`ファイル自体の読み込み失敗** — 実際には無関係だったが、この過程で
   「独自の`.ico`（PNG圧縮フレーム形式）を`System.Drawing.Icon`経由で
   タスクトレイ用に読み込むと、透過が正しく反映されず空白アイコンになる」
   という**別の実在する問題**が見つかり、こちらは実際に修正した
   （`.ico`ファイル読み込みではなく、ビットマップをその場で描画して
   `Bitmap.GetHicon()` + `Icon.FromHandle()`で変換する方式に変更）。
2. **ウイルス対策ソフト（ESET Endpoint Security）による強制終了** —
   非表示ウィンドウでのPowerShell実行・グローバルホットキー登録・
   クリップボード操作・レジストリ変更という組み合わせがヒューリスティック
   検知に引っかかっているのではと疑ったが、**Mutex実装前は同じ組み合わせの
   処理が問題なく動いていた**という指摘を受けて否定した。

## 真因

`$script:isFirstInstance`を**事前に初期化せずに**`[ref]`でMutexコンストラクタへ
渡していたことが原因だった。

```powershell
# 問題のあったコード
$script:singleInstanceMutex = New-Object System.Threading.Mutex(
    $true, "OneDriveUtils_TrayApp_SingleInstance", [ref]$script:isFirstInstance
)
```

`$script:`のような明示的スコープ修飾付きの変数を、未初期化のまま`[ref]`に
渡すと、以下のエラーで**この行自体が失敗する**：

```
[ref] は、存在しない変数に適用できません。
    + FullyQualifiedErrorId : NonExistingVariableReference
```

既定のエラー処理（`$ErrorActionPreference = 'Continue'`）ではこのエラーは
非終了エラーとして扱われ、**画面には何も表示されないまま後続の行の実行が
継続してしまう**。その結果：

- `$script:singleInstanceMutex`への代入は失敗し、Mutexは実質未作成のまま。
- `$script:isFirstInstance`も設定されないため`$null`のまま。
- 続く`if (-not $script:isFirstInstance)`が`-not $null` = `$true`と
  評価され、**本当に1つ目の起動であっても必ず「既に起動中」分岐に入る**。
- その分岐は警告ダイアログを出して即座に`exit`するため、タスクトレイ
  アイコンを作る処理（`NotifyIcon`生成）まで到達すらしない。

ローカル変数（`$isFirstInstance = $false`のように事前初期化した単純変数）を
`[ref]`に渡すテストでは問題なく動作したため、この「`$script:`スコープ修飾付き
かつ未初期化」という組み合わせに固有の問題だったと考えられる。

## 教訓・対策

- `[ref]`に渡す変数（特に`$script:`等のスコープ修飾付き変数）は、渡す前に
  必ず明示的に初期化しておく。
- 「エラーが出ているはずなのに何も起きていないように見える」場面では、
  `$ErrorActionPreference = 'Continue'`（既定）だと非終了エラーが
  画面に一瞬映るだけで後続処理が継続してしまい、原因調査が難航しやすい。
  疑わしい場合は`-ErrorAction Stop`や標準出力・エラー出力を直接ファイルへ
  リダイレクトして実行し、生のエラーメッセージを確認するのが最短経路。
  `-WindowStyle Hidden`で運用しているアプリでは特に、通常運用時には
  エラーメッセージ自体が全く目に触れないため注意。
